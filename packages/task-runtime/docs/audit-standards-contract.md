# Audit standards contract

Two independent task kinds, `audit-standard-generation` and `audit-standard-revision`, use the `audit-standards` toolset through the existing RuntimeSpec → ProviderProfile → ToolsetRegistry → SessionRuntime chain. Registration is confined to the runtime composition root; no report or supervision business code is imported by the module.

Java owns task identity, library persistence, version numbering, basis relations, user review, file return and publication. Agent inputs are immutable JSON snapshots: taskId, mode, name, category, subcategory, note, rows, sources, previousSources, targetSequences. Each source has documentId, versionId, title, kind and clauses (clause_id/text). Files are converted outside the model. New documents cannot be invented or selected by the model.

Each output row has exactly the eight source-template column names, in source order when exported. Additional output metadata lives in citations, opinions and warnings. A task-owned finalizer validates identities, source excerpts, generated row citations, complete revision opinions, unchanged row preservation and partial-regeneration scope before the generic schema judge. Source truth checks do not imply semantic audit correctness; human review remains mandatory.

Generation follows scope selection → relevant clause requirements and conditions → distinct audit items → executable procedures and aligned objectives → cited basis → self-review. Supplemental instructions restrict scope; they cannot establish regulatory obligations. Conflicts and unsupported requirements are warnings, and the model must not invent thresholds, deadlines or approval levels. Newly generated or regenerated rows require non-blank procedures and citations to versions in the current sources snapshot. Unselected rows remain unchanged. These deterministic checks do not establish clause relevance, complete coverage or semantic entailment; those remain model and business-review responsibilities.

System instructions and output contract are under `specs/audit-standards`. The main ProviderProfile role selects the model; there is no hard-coded provider. Runtime tools expose read_standard_context and check_standard_draft to the model through explicit task grants, and validate_standard_result to trusted finalization. Draft preflight returns only validity and an error, never persists or publishes content, and does not replace final validation. Prompt-guided correction allows up to two fixes within the existing turn/time limits. Added or updated revision opinions require evidence from the current sources snapshot; deletion may cite the prior requirement. Partial regeneration preserves original row order as well as unselected content. Source materials are treated as data, never runtime instructions. Runs are bounded at 240 seconds; Java grants last 300 seconds. These task kinds do not advertise checkpoint continuation; failed analyses use a new immutable task, while submission transport retries reuse clientRequestId.

The deterministic workbook codec is `scripts/audit-standards/workbook.mjs`. `node workbook.mjs read` consumes XLS/XLSX bytes on stdin and emits JSON rows; `write` consumes JSON rows and emits XLSX bytes. It uses the existing pinned SheetJS dependency, checks the single worksheet and eight column headers, rejects formulas and excessive rows, and fills actual merged cells only in the first three hierarchy columns. Java invokes it through explicit configuration, never client-supplied paths.

No new dependencies, model calls or database migrations are required by code checks. Live verification requires configured Java tables, private file volume, Pi grant issuer/public key, internal token and ProviderProfile. The Java module's interface contract describes the three business flows and frontend adaptation requirements.

Local integration verified on 2026-10-12 with an isolated PostgreSQL database and real DeepSeek deepseek-flash configured through ProviderProfile: generation, human workbook return, publication, source-version revision with one supported opinion, 1.1 publication, direct upload of the 108-row sample, idempotence, history and downloads. The Windows Java/frontend connect to a Linux container because worker process-group isolation requires POSIX. The container uses package.json pinned runtime dependencies; it does not bypass leases, citation checks or isolation. PostgreSQL state writes use sql.json with a parsed JSON value to avoid double encoding. Frontend integration used user-authorized temporary Element UI/ECharts compatibility dependencies; original Genesis distribution compatibility remains unverified.
